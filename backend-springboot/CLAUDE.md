# Backend (`com.aquamekong`)

- Services map entities to DTOs by hand with Lombok builders. `hibernate.default_batch_fetch_size` batches the lazy relations those mappers touch.
- **Auth** (`security/`): stateless JWT (`JwtService`, HS256, `JWT_SECRET`), and `POST /auth/login`, `/auth/register`, `/auth/google` and `/auth/zalo` all return a Bearer token carrying the username and roles. `SecurityConfig` is the single place for authorization rules. Read-only data GETs (`PUBLIC_READ_PATHS`) are public when `PUBLIC_READ_ENABLED` (default true); other GETs are open to `ROLE_USER`/`OPERATOR`/`ADMIN`, other writes need `OPERATOR`/`ADMIN`, `/users/**` needs `ADMIN`, and `/measurements/ingest` also accepts `X-API-Key` (`INGEST_API_KEY` → `ROLE_DEVICE`). The SSE endpoint alone accepts `?access_token=`, because `EventSource` can't send headers. An invalid or expired Bearer token gets 401 even on public routes. Passwords are BCrypt, and `password_hash` is null for accounts created through Google or Zalo. Self-registration (`REGISTRATION_ENABLED`) only ever grants `ROLE_USER`. Google sign-in (`GOOGLE_CLIENT_ID`): the frontend gets an ID token from Google Identity Services, `GoogleIdTokenVerifier` checks it against Google's JWKS (no client secret), and `ExternalAuthService` maps `sub` to a `user_identities` row. It never merges into an existing account by email (409); users link Google from `/account` instead. Zalo (`ZALO_APP_ID` + `ZALO_APP_SECRET`) is OAuth v4 + PKCE: the frontend (`auth/zaloOAuth.ts`) redirects to Zalo and checks `state` on `/auth/zalo/callback`, and `client/ZaloOAuthClient` exchanges the code server-side. Zalo gives no email, so `users.email` is nullable (V8). Passkeys (`WEBAUTHN_RP_ID`/`WEBAUTHN_ORIGINS`, V9 `user_passkeys`): `PasskeyService` wraps Yubico `RelyingParty` with discoverable credentials and required user verification, and `PasskeyChallengeStore` keeps challenges in memory for 5 minutes (single backend instance). `LoginMethodGuard` stops a user removing their last sign-in method. `AdminBootstrap` creates the first admin when `users` is empty: `ADMIN_PASSWORD`, or a random one logged once. `LoginAttemptService` locks username+IP for 5 minutes after 5 failures (429). Controller tests use `@WebMvcTest` + `@Import({SecurityConfig, JwtService, JsonAuthErrorHandler})` + `@WithMockUser`.
- **Reports** (`service/report/ReportService`): aggregate SQL via `NamedParameterJdbcTemplate`, comparing `[now-days, now)` with the previous period of the same length (`days` is clamped to 1–90). List endpoints on growing tables (measurements, alerts, forecast runs) take a capped `?limit=`. `GlobalExceptionHandler` maps errors to 400/404/502 and never returns internal messages on 500.
- The schema is owned by **Flyway** (`src/main/resources/db/migration`), and Hibernate runs with `ddl-auto: validate`. Any entity change needs a new `V{n}__*.sql` migration, and applied migrations must never be edited (checksums). V2 replaced the V1 tables. V3 seeds one virtual `CRAWLER` device per station, with `salinity`/`water_level`/`flow_rate` sensors, for the ML pipeline. V5 enforces lowercase `metric_type` with CHECK constraints, and entities normalize it via `util/MetricTypes`. V11 adds `provinces` (the 6 ĐBSCL provinces after the 2025 merger, same polygons as `frontend/src/data/mekong-provinces.json`, no entity) and fills `stations.province` from each station's location (containing province, or the nearest within ~5 km for coastal stations); ml-service does the same for stations it imports.
- "Latest value" queries are per (station, metric) and use `LATERAL ... LIMIT 1` over the `(station_id, metric_type, recorded_at DESC)` index. `StationService` drops a metric whose latest value is more than 3 days older than the station's newest reading (`STALE_METRIC_AGE`), so a metric the station stopped reporting (flow rate only exists in the old dataset) isn't shown as current.
- `MeasurementPoller` (`@Scheduled`, `app.telemetry.broadcast-interval-ms`) is the single path for new measurements, whether they come from the `/ingest` API or from rows the ML pipeline inserts directly. It evaluates alert rules (at most one ACTIVE alert per rule) and pushes each row to SSE (`TelemetryService`, `/api/v1/telemetry/stream`, events `init`/`telemetry`, 25s heartbeat).
- `POST /forecasts/predict` calls the ML service through `client/MlServiceClient` (`RestClient`, `app.ml-service.*`) outside any transaction, then saves a `forecast_run` plus its rows. `GET /forecasts/station/{id}` returns only the latest run. `DailyForecastJob` runs that 7-day prediction (ST-GNN only serves `days_ahead <= 7`) for every ACTIVE station, so anonymous users, who can't run models, still see today's forecast. It is driven by data, not a fixed hour: every 30 minutes 06:00–22:30 VN (`FORECAST_REFRESH_CRON`, `-` disables) it runs when today has no run yet or when a measurement was imported (`measurements.created_at` of the max id) after its last run, because the GitHub Actions fetch can be hours late and the host can start late; 2 minutes after startup it checks once. Its last-run time is kept in memory (seeded from the newest `forecast_run`), so a user's manual predict doesn't suppress the refresh. Each run publishes `ForecastsRefreshedEvent`. `spring.task.scheduling.pool.size` is 4 so that job never blocks `MeasurementPoller`.
- **Push notifications** (`service/push/`, V10 `push_subscriptions`): `AlertService` publishes `AlertCreatedEvent` when it creates an alert, and `PushService.onAlertCreated` sends it after commit on the bounded `pushExecutor` (`config/PushConfig`), so the poller never waits on the network. A new alert goes to staff (`ROLE_ADMIN`/`ROLE_OPERATOR`), to accounts watching that station, and to accounts that watch no station (`PushSubscriptionRepository.findAlertRecipients`). `PushService.notifyStaff` sends operational messages only to devices of `ROLE_ADMIN`/`ROLE_OPERATOR` accounts. `WebPushSender` implements RFC 8291 encryption + VAPID with JDK crypto only (`VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY`, checked as a pair at startup). `FcmSender` calls the FCM HTTP v1 API with a service-account JWT (`FIREBASE_SERVICE_ACCOUNT_BASE64`) and caches the access token. Either channel is off when its env is empty. Web Push endpoints are restricted to known browser push hosts (`PushService.WEB_PUSH_HOSTS`) because the backend POSTs to them (SSRF). Devices that answer 404/410/UNREGISTERED are deleted.
- **Data freshness** (`service/report/DataFreshnessService`, public `GET /reports/data-freshness`): after `app.freshness.expected-by` (12:00 VN, since the GitHub schedule can be hours late) yesterday's daily reading must exist, otherwise `stale` (only ACTIVE stations count). The Overview page shows a banner, and `DataFreshnessJob` (`FRESHNESS_CHECK_CRON`, default 12:00, `-` disables) pushes a notice to staff, because the RYNAN pipeline (GitHub Actions → Drive → ml-service) can stop silently.
- **Station watches** (`service/watch/`, V12 `station_watches`, `/api/v1/watches` for any signed-in user): an account watches up to 20 stations, each with its own salinity threshold (the frontend suggests one per crop). `StationWatchService.outlook` compares it with the latest salinity reading (ignored when older than 3 days) and the latest forecast run from today on. `StationWatchJob` (on every `ForecastsRefreshedEvent`) pushes to the account only when `exceeding` differs from the stored `forecast_exceeding`, so a station that stays above the threshold all dry season isn't reported every day. Saving a watch stores the current state, so the next report is a real change.
- **Forecast accuracy** (`service/forecast/ForecastAccuracyService`, public): `GET /forecasts/accuracy` relays the ML service backtest; `GET /forecasts/station/{id}/verification` pairs stored forecasts (the latest run of each VN day, only dates after the run day) with that day's max salinity reading, so it fills in as daily readings arrive.
