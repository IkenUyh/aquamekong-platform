# Backend (`com.aquamekong`)

- Services map entities to DTOs by hand with Lombok builders. `hibernate.default_batch_fetch_size` batches the lazy relations those mappers touch.
- **Auth** (`security/`): stateless JWT (`JwtService`, HS256, `JWT_SECRET`), and `POST /auth/login`, `/auth/register`, `/auth/google` and `/auth/zalo` all return a Bearer token carrying the username and roles. `SecurityConfig` is the single place for authorization rules. Read-only data GETs (`PUBLIC_READ_PATHS`) are public when `PUBLIC_READ_ENABLED` (default true); other GETs are open to `ROLE_USER`/`OPERATOR`/`ADMIN`, other writes need `OPERATOR`/`ADMIN`, `/users/**` needs `ADMIN`, and `/measurements/ingest` also accepts `X-API-Key` (`INGEST_API_KEY` → `ROLE_DEVICE`). The SSE endpoint alone accepts `?access_token=`, because `EventSource` can't send headers. An invalid or expired Bearer token gets 401 even on public routes. Passwords are BCrypt, and `password_hash` is null for accounts created through Google or Zalo. Self-registration (`REGISTRATION_ENABLED`) only ever grants `ROLE_USER`. Google sign-in (`GOOGLE_CLIENT_ID`): the frontend gets an ID token from Google Identity Services, `GoogleIdTokenVerifier` checks it against Google's JWKS (no client secret), and `ExternalAuthService` maps `sub` to a `user_identities` row. It never merges into an existing account by email (409); users link Google from `/account` instead. Zalo (`ZALO_APP_ID` + `ZALO_APP_SECRET`) is OAuth v4 + PKCE: the frontend (`auth/zaloOAuth.ts`) redirects to Zalo and checks `state` on `/auth/zalo/callback`, and `client/ZaloOAuthClient` exchanges the code server-side. Zalo gives no email, so `users.email` is nullable (V8). Passkeys (`WEBAUTHN_RP_ID`/`WEBAUTHN_ORIGINS`, V9 `user_passkeys`): `PasskeyService` wraps Yubico `RelyingParty` with discoverable credentials and required user verification, and `PasskeyChallengeStore` keeps challenges in memory for 5 minutes (single backend instance). `LoginMethodGuard` stops a user removing their last sign-in method. `AdminBootstrap` creates the first admin when `users` is empty: `ADMIN_PASSWORD`, or a random one logged once. `LoginAttemptService` locks username+IP for 5 minutes after 5 failures (429). Controller tests use `@WebMvcTest` + `@Import({SecurityConfig, JwtService, JsonAuthErrorHandler})` + `@WithMockUser`.
- **Reports** (`service/report/ReportService`): aggregate SQL via `NamedParameterJdbcTemplate`, comparing `[now-days, now)` with the previous period of the same length (`days` is clamped to 1–90). List endpoints on growing tables (measurements, alerts, forecast runs) take a capped `?limit=`. `GlobalExceptionHandler` maps errors to 400/404/422/502 (422 when ml-service refuses a station with too few recent readings, `InsufficientDataException`) and never returns internal messages on 500.
- The schema is owned by **Flyway** (`src/main/resources/db/migration`), and Hibernate runs with `ddl-auto: validate`. Any entity change needs a new `V{n}__*.sql` migration, and applied migrations must never be edited (checksums). V2 replaced the V1 tables. V3 seeds one virtual `CRAWLER` device per station, with `salinity`/`water_level`/`flow_rate` sensors, for the ML pipeline. V5 enforces lowercase `metric_type` with CHECK constraints, and entities normalize it via `util/MetricTypes`. V11 adds `provinces` (the 6 ĐBSCL provinces after the 2025 merger, same polygons as `frontend/src/data/mekong-provinces.json`, no entity) and fills `stations.province` from each station's location (containing province, or the nearest within ~5 km for coastal stations); ml-service does the same for stations it imports.
- "Latest value" queries are per (station, metric) and use `LATERAL ... LIMIT 1` over the `(station_id, metric_type, recorded_at DESC)` index. `StationService` drops a metric whose latest value is more than 3 days older than the station's newest reading (`STALE_METRIC_AGE`), so a metric the station stopped reporting (flow rate only exists in the old dataset) isn't shown as current.
- `MeasurementPoller` (`@Scheduled`, `app.telemetry.broadcast-interval-ms`) is the single path for new measurements, whether they come from the `/ingest` API or from rows the ML pipeline inserts directly. It evaluates alert rules (at most one ACTIVE alert per rule) and pushes each row to SSE (`TelemetryService`, `/api/v1/telemetry/stream`, events `init`/`telemetry`, 25s heartbeat).
- `POST /forecasts/predict` calls the ML service through `client/MlServiceClient` (`RestClient`, `app.ml-service.*`) outside any transaction, then saves a `forecast_run` plus its rows. `GET /forecasts/station/{id}` returns only the latest run. `DailyForecastJob` runs that 7-day prediction (ST-GNN only serves `days_ahead <= 7`) for every ACTIVE station, so anonymous users, who can't run models, still see today's forecast. It is driven by data, not a fixed hour: every 30 minutes 06:00–22:30 VN (`FORECAST_REFRESH_CRON`, `-` disables) it runs when today has no run yet, when a measurement was imported (`measurements.created_at` of the max id) after its last run, because the GitHub Actions fetch can be hours late and the host can start late, or when the ML risk model's `trainedAt` (`MlServiceClient.earlyWarning`) differs from the one seen at its last run, because the model retrains minutes after new readings arrive or after a deploy; 2 minutes after startup it checks once. The model stamp starts unknown, so the first check after a restart that can read it reruns once. Its last-run time is kept in memory (seeded from the newest `forecast_run`), so a user's manual predict doesn't suppress the refresh. Each run publishes `ForecastsRefreshedEvent`. `spring.task.scheduling.pool.size` is 4 so that job never blocks `MeasurementPoller`.
- **Push notifications** (`service/push/`, V10 `push_subscriptions`): `AlertService` publishes `AlertCreatedEvent` when it creates an alert, and `PushService.onAlertCreated` sends it after commit on the bounded `pushExecutor` (`config/PushConfig`), so the poller never waits on the network. A new alert goes to staff (`ROLE_ADMIN`/`ROLE_OPERATOR`), to accounts watching that station, and to accounts that watch no station (`PushSubscriptionRepository.findAlertRecipients`). `PushService.notifyStaff` sends operational messages only to devices of `ROLE_ADMIN`/`ROLE_OPERATOR` accounts. `WebPushSender` implements RFC 8291 encryption + VAPID with JDK crypto only (`VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY`, checked as a pair at startup). `FcmSender` calls the FCM HTTP v1 API with a service-account JWT (`FIREBASE_SERVICE_ACCOUNT_BASE64`) and caches the access token. Either channel is off when its env is empty. Web Push endpoints are restricted to known browser push hosts (`PushService.WEB_PUSH_HOSTS`) because the backend POSTs to them (SSRF). Devices that answer 404/410/UNREGISTERED are deleted.
- **Data freshness** (`service/report/DataFreshnessService`, public `GET /reports/data-freshness`): after `app.freshness.expected-by` (12:00 VN, since the GitHub schedule can be hours late) yesterday's daily reading must exist, otherwise `stale` (only ACTIVE stations count). The Overview page shows a banner, and `DataFreshnessJob` (`FRESHNESS_CHECK_CRON`, default 12:00, `-` disables) pushes a notice to staff, because the RYNAN pipeline (GitHub Actions → Drive → ml-service) can stop silently.
- **Station watches** (`service/watch/`, V12 `station_watches`, `/api/v1/watches` for any signed-in user): an account watches up to 20 stations, each with its own salinity threshold (the frontend suggests one per crop). `StationWatchService.outlook` compares it with the latest salinity reading (ignored when older than 3 days, and then the station's forecasts are ignored too, like ml-service, which refuses to forecast it; a flagged `risk_until` day is still kept) and the latest forecast run for today..today+7: the forecast value, and `salinity_forecasts.risk_salinity` (V13, the ML risk model's "may reach" level). A day flagged by the risk level stays flagged until it has passed (`station_watches.risk_until`, V13), so a level that dips for a day doesn't send "đã giảm" right before salinity crosses; ml-service `app/early_warning/episodes.py` scores the same rule on past dry seasons, keep them in sync. `StationWatchJob` (on every `ForecastsRefreshedEvent`) pushes to the account only when `exceeding` differs from the stored `forecast_exceeding`, so a station that stays above the threshold all dry season isn't reported every day. Saving a watch stores the current state, so the next report is a real change. `station_watches.min_threshold` (V14, optional, must be below `threshold`) is the lower bound for ranges like shrimp farming: a fresh reading or a forecast below it also makes `exceeding` true (`firstBelowDate`, `forecastMin`), and the push says "Độ mặn thấp". The risk level only bounds salinity from above, so it plays no part there, and ml-service `episodes.py` only scores the upper threshold.
- **Crops** (`service/crop/`, V14 `crops` + `crop_stages`, public `GET /api/v1/crops`): the reference table of crops and water uses (domestic water, shrimp), seeded by the migration with a source for every number; fix or add data with a new migration. Each crop has ordered stages with the Vietnamese warning threshold (`max_salinity`, `min_salinity` for ranges) and either fixed `duration_days`, `flexible` (takes the variety's remaining days; one per crop), or neither (no source for its length yet, merged into the next flexible stage). `crops.fao_ecw_*` keep FAO 29 Table 4 ECw values as printed (dS/m at 100/90/75/50% yield); the API also returns them in ‰ (× 0.64). The migration also cleared `station_watches.crop` names that are no longer in the table (kept as a custom threshold). `CropStages.current` gives the stage for a sowing date and variety length.
- **Field profiles** (`service/field/`, V15 `field_profiles`, `/api/v1/fields`; since V16 shared server-wide and `permitAll`: anyone, guests included, lists, adds, edits and deletes any field, capped at 1000 fields in total; `user_id` is the account that added it, NULL for guests, and only those fields get a station watch and push; `GET` returns each field's stage thresholds with the station `outlook`, reading each station once): station nearest the field (picked by GPS on the device; coordinates never reach the backend), crop and variety with its day count, sowing date, area, fresh-water pond and its volume. A multi-stage crop (rice) requires the sowing date and a variety longer than its fixed stages. Saving a field calls `StationWatchService.syncFieldWatch`, which keeps one `station_watches` row per field (`field_profile_id`, deleted with the field) with the current stage's thresholds; it recomputes the reported state only when the station or thresholds change. `UNIQUE (user, station)` now only applies to manual watches (partial index), so two fields at one station each have their own thresholds, and a field's watch can't be removed through `/watches`. The 20-watch limit counts field watches too. On every run `StationWatchJob.applyStageThreshold` moves a field's watch to its stage's thresholds for today (e.g. when rice reaches panicle initiation) before comparing, keeping the stored state, so a crossing caused by the new threshold is reported in that same run.
- **Salinity exposure** (`service/field/SalinityExposure` (pure) + `SalinityExposureService`, public `GET /api/v1/fields/{id}/exposure`, 204 when it can't be estimated): what the crop has taken if irrigated with its station's water, from the station's daily max salinity (VN day). Only `CROP` category. Season: multi-stage crops (rice) from the sowing date for the variety's days; other crops the dry season 01/12–31/05 (the current one, or the last one from June to November). Threshold: FAO 100% yield level in ‰; crops without FAO numbers use the stage's `max_salinity` and get no yield %. Cumulative = Σ (daily max − threshold) × `crop_stages.salt_sensitivity` (V17) of that day's stage; effective salinity = threshold + cumulative / season length, then linear interpolation on the FAO 100/90/75/50% points (past 50% the last segment is extended, capped at 100%). Days without readings add nothing, and `daysWithData` is returned. The rice coefficients (1,5 / 1 / 1,5 / 0,5) are set by the app from a qualitative ranking (sources say which stages are sensitive, not by how much), chosen so their mean over a rice season stays near 1 and steady salinity still gives FAO's loss. The response also carries `damage` (an estimate, V18): area × yield loss % × normal yield × price, rounded to 1,000 đ, plus what 1% of the field's yield is worth and the whole season's value. The field's own `yield_t_ha`/`price_vnd_kg` win over the crop's `default_yield_t_ha`/`default_price_vnd_kg` (each with its source, the price with `price_as_of`; only rice has defaults so far, other crops have no recent sourced Mekong figures); a missing number leaves the amounts null, and `damage` is null when there is no yield %. Refresh the default price with a new migration.
- **Recommendations** (`RecommendationService`, public): stations above 4‰ now (readings older than 3 days ignored), then stations below it whose forecast or risk level exceeds 4‰ within 7 days ("Trữ nước ngọt trước ngày ..."), from `SalinityForecastRepository.findLatestRunForecastsBetween`.
- **Replay** (`service/report/ReplayService`): besides recomputing alerts from measurements, it asks the ML service for the early warnings the app would have sent in that range (`MlServiceClient.earlyWarningEpisodes`, each station's own threshold; only dry seasons the risk model was re-run on). They become `WARNED` events, `OPENED` events get `warnedDaysAhead`, and `earlyWarning` sums them up. `replay()` is not transactional so the ML call holds no DB connection; when the ML service fails the replay still works, with `earlyWarning.available = false`.
- **Forecast accuracy** (`service/forecast/ForecastAccuracyService`, public): `GET /forecasts/accuracy` relays the ML service backtest; `GET /forecasts/early-warning` relays the risk model's per-season early-warning scores (404 until its first training); `GET /forecasts/station/{id}/verification` pairs stored forecasts (the latest run of each VN day, only dates after the run day) with that day's max salinity reading, so it fills in as daily readings arrive.
